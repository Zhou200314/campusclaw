# Design: add-auth-session-materials

## Context

迭代 1 的判定标准不是界面是否好看，而是：**能登录、能隔离、能上传入库、第三方能按 README 复现**。
因此访问控制必须落在接口层，界面只作为入口。

## Decisions

### D1 会话 Cookie 而不是 JWT

浏览器同源站点使用 HttpOnly + SameSite=Lax 的会话 Cookie，服务端保存会话行。
理由：登出只需删除会话行即可立即失效；角色与班级不进入客户端载荷，避免被当成授权依据。

### D2 会话只存令牌散列

`sessions.id` 存 `sha256(令牌)`，数据库被读取也无法直接重放会话。

### D3 登录成功换发会话 ID

登录处理先删除请求携带的旧会话行，再签发新会话，防止会话固定攻击。

### D4 统一失败响应

用户不存在、口令错误、锁定期内三种情况返回**完全一致**的 401 响应体（`INVALID_CREDENTIALS`）；
用户不存在时仍执行一次等价耗时的 scrypt 比较，避免用响应耗时枚举账号。

### D5 班级是租户边界

所有材料查询强制带上会话中的 `class_id`；跨班按 ID 访问与不存在同形返回 404，不泄露对方标题与正文。

### D5.1 跨班可见性可配置

默认 `CROSS_CLASS_VISIBLE=0`：跨班完全隔离，按 ID 访问与下载一律 404，符合本迭代的班级隔离验收。
设为 `1` 时进入演示模式：列表可看到其他班级材料标题，但详情不下发正文、下载返回 403。
两种模式的差异只体现在"拒绝方式"上——跨班一律不可获取文件内容与正文，数据边界不变。

### D6 配置外置、失败即停

`SESSION_SECRET` 缺失或过短时服务端启动失败，不提供内置默认密钥；`.env` 不入库，`.env.example` 必须入库。

### D7 数据层可替换

默认使用 SQLite（免 Docker 演示）。仓储接口不使用方言特有语法，替换为 MySQL 时只需改 `db.js`。

## Alternatives considered

| 方案 | 结论 |
| --- | --- |
| JWT + localStorage | 否决。XSS 可读、登出无法立即失效、载荷易被当成授权依据 |
| 内置开发默认密钥 | 否决。等于把会话签发权交给任何人 |
| 前端切换角色/班级 | 否决。客户端声明不可信，必须由服务端会话决定 |
| 先做界面再补鉴权 | 否决。界面完备但接口可绕过，不算实现访问控制 |
| 直连向量库做 RAG | 否决。没有可靠的入库与隔离，检索会造成跨班泄露 |
