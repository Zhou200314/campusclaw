# 文件上传逻辑与文件类型支持的文字分析

## 一、文件上传逻辑分析

本迭代的上传接口在实现上要同时满足三个约束：只有教师可以上传、材料只能落在本班、材料记录与知识库条目必须同时写入或同时不写入。这三个约束直接决定了处理的先后顺序——鉴权与授权必须排在文件处理之前，班级信息必须来自服务端会话而不是请求参数，两次数据库写入必须包在同一个事务里。理解这一点之后，接口的每一个环节都是可以推导出来的，而不是随意安排的。

从流程上看，客户端以 multipart/form-data 提交请求，服务端先做会话校验，未登录直接返回 401；再校验角色，学生会话在**读取文件之前**就被拒绝并返回 403。把角色校验放在文件处理之前是刻意的：如果先收文件再判断权限，等于允许任何登录用户消耗服务器的内存与磁盘，权限检查也就形同虚设。通过授权后，文件由 multer 以内存方式解析，并施加两个硬性限制：单文件大小不超过 UPLOAD_MAX_BYTES（默认 10 MB），一次请求只接受一个文件。选择内存存储而不是直接写盘，是因为正文提取需要拿到完整内容，而且只有在角色、班级、大小全部校验通过之后才应该产生落盘这样的副作用；代价是文件在内存中被完整复制一次，所以大小上限不能设得太大。

校验通过后进入文件名处理环节。上传者提供的文件名不可信，可能包含路径分隔符或 Windows 非法字符，因此实现先用 path.basename 截取最后一段，再把 \ / : * ? " < > | 以及控制字符统一替换为下划线，最后限制总长度。这样即使客户端伪造出 ../../evil.txt 这类名字，也只会落成一个普通文件名，无法跳出上传目录。落盘路径设计为 uploads/<班级 ID>/<UUID>-<净化后的文件名>：班级 ID 目录本身就是数据边界，UUID 前缀则避免同名文件互相覆盖。

紧接着是正文提取，它的结果决定知识库中写入什么内容（详见第二部分）。随后的数据库写入被包在 BEGIN IMMEDIATE 与 COMMIT 之间：先在 materials 表插入一行材料记录，再在 knowledge_entries 表插入一行知识库条目，两步都成功才提交。这样做的意义在于，材料与知识条目在业务上是一体两面——有材料却没有知识条目，后续检索会丢内容；有知识条目却没有材料，列表里就会出现无法下载的"幽灵条目"。事务保证了这种情况不会出现。如果写入过程中任意一步失败，实现会回滚事务并删除已经落盘的文件，避免留下"只有文件没有记录"的垃圾数据；这一处仍有改进空间，因为回滚清理只覆盖了异常路径，如果进程在落盘之后、提交之前崩溃，孤儿文件依然可能残留，更稳妥的做法是先写临时文件、事务提交后再改名到位。

最后是响应设计。成功时返回 201，同时给出材料编号与知识库条目编号，前端据此提示"材料 #5 与知识库条目 #1 已在同一事务写入"，让上传结果可核对而不是只给一句"成功"。失败路径则按原因区分：未登录 401、学生上传 403、超过大小上限 413、缺少文件或字段名不对 400。下载接口复用同一套鉴权与班级过滤逻辑，并且响应头使用 Content-Disposition: attachment，强制按附件下载，这样即使有人上传 HTML 或 SVG，也不会在浏览器里被当作页面内联执行。

## 二、支持文件类型的分析

讨论"支持哪种文件类型"时，必须先明确一个前提：本接口在传输与存储层面并不限制类型，真正区分"支持"与"不支持"的是**正文提取**，也就是文件内容能不能进入知识库、从而被列表搜索检索到。这个区分之所以重要，是因为如果不加说明就说"支持所有文件"，会让人误以为 Word 和 PDF 的内容也能被搜到；而如果直接说"只支持 txt 和 md"，又会低估实际覆盖面。

正文提取的实现采用三道判定，顺序固定。第一道是扩展名白名单：当文件名的扩展名命中 .txt、.md、.markdown、.csv、.tsv、.json、.log、.yml、.yaml、.html、.htm、.tex、.srt、.vtt 之一时，直接按 UTF-8 解码为正文，并剥离可能存在的 BOM 头。第二道是内容嗅探：扩展名不在白名单时，取文件的前 4 KB 判断它"像不像文本"——只要这一段里没有出现 NUL 字节（0x00），并且控制字符所占比例低于 5%，就认为它是文本并同样提取。第三道是兜底：以上两条都不满足的，判定为二进制文件，正文位置只写入"未提取正文"的占位说明与来源文件名。选择用"是否含 NUL 字节"作为主要判据，是因为绝大多数二进制格式（图像、压缩包、Office 文档、可执行文件）内部都包含大量 0x00，而纯文本几乎不会出现该字节；再用控制字符比例作为辅助，是为了容忍少量异常字符而不至于把正常的文本误判成二进制。

这套判定在实际测试中的表现与预期一致。md、csv、html 等白名单内的文件都被正确提取；扩展名陌生甚至没有扩展名的纯文本文件（例如 .xyz 和无扩展名文件）也被内容嗅探救回并成功入库，说明白名单不是唯一的判定途径，覆盖面比"只认扩展名"更宽；而真实的 PNG、PDF、docx 与 exe 文件都被判定为二进制，只登记来源信息、不写入正文。同时测试也暴露了嗅探启发式的边界：当二进制文件恰好在前 4 KB 内不含 NUL 字节时，它会被误判为文本，把乱码写进知识库。这说明启发式判定只能覆盖大多数常见情况，无法做到绝对准确，若要更可靠，应当结合文件头的魔术字节（如 PNG 的 89 50 4E 47、ZIP/docx 的 50 4B 03 04、PDF 的 %PDF、可执行文件的 MZ）来判断，或者直接引入成熟的文件类型识别库。

## 三、txt、md 以外文件是否支持的分析

回答这个问题需要分两个层面，否则很容易给出自相矛盾的结论。

第一个层面是上传、存储与下载。这个层面上答案是"支持"，因为接口没有设置任何扩展名或 MIME 类型白名单，任何类型的文件都能成功上传，按班级目录落盘，之后也可以正常下载。实测中 docx、pdf、png 甚至 exe 都返回 201 并成功保存，说明接口并不会因为"类型不认识"而拒绝文件。

第二个层面是知识库入库，也就是正文能否被搜索到。这个层面上答案是"只支持文本类"。在 txt 与 md 之外，还支持 csv、tsv、json、log、yml、yaml、html、htm、tex、srt、vtt 共 12 种文本扩展名，并且通过内容嗅探还能覆盖任意扩展名或无扩展名的纯文本文件。不支持的是 Word（docx/doc）、PDF、Excel（xlsx）、PPT、图片、压缩包等二进制格式：它们可以上传、可以下载、在材料列表里也能看到文件名，但由于没有提取正文，用关键字搜索内容时不会命中。这恰好符合本迭代的 Non-goals——知识库只负责把正文存下来，不做检索、问答与向量化，正文提取的完整性因此可以留到后续迭代再加强。

因此，对"txt、md 以外的文件是否支持"这一问题的完整回答是：在存储与下载意义上支持全部类型，在正文入库意义上支持全部文本类文件（含扩展名白名单之外的纯文本），但不支持二进制文档的正文提取。判断一个具体文件属于哪一档，可以用 scripts/probe-file-types.mjs 实测确认，脚本会在运行结束后清理测试数据。

## 四、不足与改进方向

从分析结果看，当前实现有四处值得改进。第一处是编码处理，正文目前只按 UTF-8 解码，而国内教研场景中大量文档来自 Word 或老系统，常为 GBK/GB18030 编码，这类文件目前会被解成乱码入库，实测把 GBK 编码的"中文测试"存成了无法识别的字符序列。改进方式是引入编码嗅探：有 BOM 时按 BOM 判断，无 BOM 时先尝试 UTF-8，失败后回退 GB18030。第二处是扩展名与内容的优先关系，目前扩展名命中白名单就直接当作文本解码，导致把二进制文件改名成 .txt 后会被写入乱码，而且由于底层数据库驱动会在首个 NUL 字节处截断字符串，四十九字节的文件最终只存下三个字符；更稳妥的做法是让二进制判定优先于扩展名，并在写入前过滤含 NUL 的内容。第三处是安全与运维层面的缺失：目前没有可执行文件黑名单，没有按班级或按用户的容量配额，也没有病毒扫描与同内容去重，这些在单机演示环境下影响有限，但一旦对外提供服务就应当补齐。第四处是正文提取的覆盖范围，docx 与 pdf 这类教研材料的主要载体尚未支持，可分别借助 mammoth 与 pdf 解析库补齐，这也是知识库能否真正"用起来"的关键一步。
