# 文件下载权限与实现逻辑（文字分析）

下载是否需要权限，取决于把下载看成什么。如果把下载仅仅当作"把服务器上的文件发给浏览器"，它似乎只是一个静态资源请求；但在本项目里，材料是按班级隔离的教研数据，下载接口是数据离开系统的主要出口，一旦这里不设边界，前面所有的列表过滤与详情校验都可以被绕过——攻击者不需要看列表，只要依次猜测数字 ID 去下载即可。因此实现上把下载与列表、详情放在同一套访问控制之下，要求请求者必须处于有效的登录会话中，并且只能下载属于自己班级的材料。

具体实现按顺序做四件事。请求进入 `GET /api/materials/:id/download` 后，首先执行鉴权中间件：从 Cookie 中取出会话令牌，与服务端 sessions 表中保存的令牌散列比对并检查有效期，任何一步不通过都直接返回 401，而且响应体里只有"未登录或会话已失效"，不包含材料标题、正文或任何磁盘路径。鉴权通过后，班级边界从会话中读取，也就是使用 `req.user.classId`，而不是从查询参数或请求体中取班级；这一点很关键，因为如果班级可以由请求方指定，那么隔离就退化成了一句声明，改一个参数就能读到别班的数据。接着是查询环节，代码执行 `SELECT * FROM materials WHERE id = ? AND class_id = ?`，把班级作为 SQL 条件的一部分，而不是先把记录查出来再在应用层判断"这条属于别的班吗"；这样既能避免因为漏写判断而越权，也让越权查询根本查不到记录。最后是文件返回环节：先确认这条记录确实有 stored_path，且磁盘上的文件仍然存在，然后用 `res.download()` 返回，把数据库里保存的原始文件名作为下载名，并让响应头带上 `Content-Disposition: attachment`，强制浏览器按附件处理而不是内联打开。

这套实现的实际效果通过八种场景验证过。不带 Cookie 直接请求下载返回 401；用本班教师的会话下载本班材料返回 200，且拿到的字节与上传时完全一致；换成本班学生的会话同样是 200，因为本迭代的角色边界是"学生可以查看与下载，只有上传被禁止"，下载并不按角色区分。用高一(1)班的教师会话去下载高一(2)班的材料返回 404，用一个不存在的 ID 返回 404，用一个非数字的 ID 同样返回 404，三者响应体完全一致；用已经登出的旧 Cookie 再请求则回到 401，说明服务端删除会话行之后旧令牌立即失效。

从设计取舍上看，有几个地方是刻意为之。第一，跨班访问与不存在的记录返回完全相同的 404 文案，而不是"无权访问"这类更具体的提示，这是为了防止通过状态码或提示文案的差异来枚举其他班级有哪些材料 ID，也就是把越权与不存在这两种情况在外部表现上合并成一种。第二，班级条件写进 SQL 而不是写在业务判断里，是把安全边界下沉到数据访问层，减少遗漏的机会。第三，下载强制以附件形式返回而不是内联展示，是为了降低上传内容带来的风险——如果有人上传了 HTML 或 SVG，内联打开就可能在浏览器里执行脚本，而附件下载不会。第四，磁盘上的文件名是"随机前缀加净化后的原文件名"，对外展示与下载用的是数据库里的原始文件名，这样既避免同名文件互相覆盖，也不会把服务器的目录结构暴露出去。

当然，这套实现也有不足。种子里预置的四条材料在数据库中有文件名，但磁盘上并没有对应的真实文件，因此它们虽然出现在列表里，下载时却会返回 404，而"材料存在但没有附件"与"材料根本不存在"共用同一条文案，语义上不够精确，改进方式是让种子阶段同时写入真实文件，或者在列表和详情里明确标注"无附件"。此外，下载目前没有独立的频次限制、审计日志与下载次数统计，也没有做水印或防转发设计，这些在单机演示环境下影响不大，但如果后续要对外提供服务，应当配合日志与限流一起补上。
